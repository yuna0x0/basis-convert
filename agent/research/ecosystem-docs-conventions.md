# How this ecosystem writes READMEs and docs

Read 2026-08-30, from the packages themselves rather than from advice about them. Sources:
Modular Avatar and NDMF (`bdunderscore`), Avatar Optimizer (`anatawa12`), VRCFury, Jiggle Physics
(which ships inside Basis), the Basis repository, and Haï's product site.

## READMEs are pointers, not manuals

Every one of them is short, and none doubles as documentation.

| Package | What its README contains |
|---|---|
| Modular Avatar | Badges, logo, one sentence defining it, one sentence on what using it feels like, a demo video, three feature bullets, a link to the docs site. No installation, no license section, no status. |
| Avatar Optimizer | Badges, one paragraph, where to ask for support, docs links in two languages, a note on API stability. |
| VRCFury | Three links: download, documentation, Discord. Plus a licence note. Around 80 words. |
| NDMF | Badges, one-line definition, feature bullets, then developer-facing architecture, because its audience is people writing plugins against it. |
| Jiggle Physics | An OpenUPM badge, one line defining it, features each illustrated with a video or screenshot, a two-line install snippet. |

What none of them has: a status section, a roadmap, a description of internal layers, test counts,
or a list of what is not implemented yet. That belongs in the issue tracker or the docs, and the
audience for a README is someone deciding in ten seconds whether this tool is for them.

The shape they share: **name, one sentence saying what it is, a few lines on what it does, then a
link to where the real documentation lives.**

## The docs site is where the manual lives

Modular Avatar's is Docusaurus 3 in `docs~/` (the tilde keeps Unity out of it), sidebar
autogenerated from the folder structure, `en` and `ja` locales, images stored beside the markdown
that uses them. Avatar Optimizer uses Hugo with the `hugo-book` theme in `.docs/`, same idea.

Modular Avatar's page layout is worth copying directly:

- `intro.md`: what it is in two sentences, then installation, then "what to read next" pointing
  at tutorials.
- `tutorials/`: task-shaped, one page per thing a person wants to accomplish.
- `reference/`: one page per component, each following the same skeleton, and each opening with a
  screenshot of the component:
  - a sentence defining it
  - **When should I use it?**
  - **When shouldn't I use it?**
  - how to set it up, with screenshots
  - **What does it do, exactly?** for the mechanism
- `faq.md`, `upgrading.md`, `changelog.md`.

Installation instructions live in the docs, not the README, and are written per client: ALCOM
first, VCC second, each with its own screenshots.

## What this means for us

- Both READMEs get cut to a pointer. What the package converts belongs in the docs; what state
  the project is in belongs nowhere user-facing.
- The docs site follows Modular Avatar's structure, since a person coming to this tool has
  probably used it.
- Reference pages are written per source component rather than per internal stage. A reader cares
  that PhysBones become jiggle physics, not that readers, mappers and writers are separate.
- Screenshots carry the walkthrough. Our own window is the thing people need to recognise.

## A raw img tag loses the baseUrl

`window-scanned.webp` is portrait, 1438x1906, and ran about 1000px tall at column width. Capping
it with a raw `<img src="/img/window-scanned.webp" width="480" />` broke it: markdown images go
through Docusaurus's asset loader and come out `/watari-basis/assets/images/<name>-<hash>.webp`,
a raw tag keeps the path as written, and the site is served under `/watari-basis/`. It 404d on
the published site while the local build looked correct, because the check was that the tag
survived the build rather than that the path resolved.

It is now a markdown image inside `<div className="screenshot-tall">`, capped in `custom.css` at
`width: 100%; max-width: 480px`. Both are needed: `max-width` alone is more specific than
Infima's `img { max-width: 100% }` and overflows a phone. Recorded in
`docs/static/img/PLACEHOLDERS.md`.

The file was also re-encoded to 960 wide during this, and put back. Screenshots are capped in
the page, not in the file.

## An imported .vrm converted as though it were empty

A VRM 1.0 avatar dragged into a scene from its `.vrm` file produced nothing: 0 spring chains, 0
expressions, no licence, no eye offset, and it was called a "Humanoid avatar" rather than a VRM
one. On AvatarSample_B that was 90 spring joints, 12 collider groups and 18 expressions ignored.

The cause is the file, not the components. Everything was read from YAML, and a `.vrm` is binary
glTF behind a ScriptedImporter, so the scanner found no documents and the source read as empty.
Nothing reported it either: `source.notUnpacked` only fires for a prefab that is a variant of a
model, and here the scene object is the model instance itself.

`VrmComponentReader` reads the same data from the live components. UniVRM has to be installed for
the file to import, so the components are real types and their serialized fields carry what the
text would have. Identifiers are each object's own local file id inside the asset, which is what
`PrefabObjectResolver` already indexes, so the mappers, the resolver and the writers did not
move. Recognition goes through the same script-guid table. See `agent/decisions/0015`.

Both formats are covered. VRM 1.0 was verified end to end; the 0.x component path is written from
the same field names the text reader uses but is untested, because UniVRM 0.x is not installed
here and a current UniVRM migrates a 0.x file to 1.0 components as it imports.

The extraction step went too. A prefab saved from a `.vrm` without "Extract Meta And Expressions"
used to report `vrm.objectUnreadable`; the instance component is live, so the object asset is now
read through it. The diagnostic stays for the case where the component cannot be resolved.

On AvatarSample_B: 22 chains to 22 jiggle rigs, 28 colliders, 18 expressions of which 5 became
Vixxy controls and 13 were left to Basis, the eye position from its look at offset, and the
licence read. Converting wrote 28 components and skipped none.

Not done, and worth doing next: a VRM's five viseme expressions and its blink could fill in the
`BasisAvatar` viseme and blink slots, which today are left for the user to assign by hand. VRM
has five vowels where VRChat has fifteen visemes, so it is a partial fill and needs a decision
about the ten it cannot name.

## VRM 0.x never needed the component reader, and a real 0.x avatar proved it

UniVRM 0.x installs no ScriptedImporter. Its `vrmAssetPostprocessor` watches for a `.vrm` landing
in the project and writes a real `.prefab` beside it, with the textures, materials and blendshape
assets extracted as project files. So a 0.x avatar is Unity YAML from the start and the text
reader has always been the right one. The component path written yesterday is a fallback for 0.x,
not its route.

Verified by installing `com.vrmc.univrm` 0.131.2 through OpenUPM against a real
`AvatarSample_B` exported as VRM 0.x. `com.vrmc.vrm` had to come out first: its importer claims
the `.vrm` extension unconditionally, and with migration off it parses a 0.x file as nothing.

The generated prefab converted the same as the 1.0 avatar: 22 chains to 22 jiggle rigs, 28
colliders, 18 expressions, 5 Vixxy controls, 28 components written and none skipped. Reading the
same prefab through the component reader gave the same 22 chains, 12 collider groups and 18
expressions, so both readers agree on a real 0.x avatar as well as on the fixtures.

Two components were unrecognised: `VRMHumanoidDescription`, which is 0.x's own record of what
Unity's avatar holds, and the look at pair. Both are named now, and look at is reported as
`vrm.lookAt` since Basis drives gaze from the eye bones.

Headless note: the 0.x postprocessor finishes in `EditorApplication.delayCall`, which never runs
in a batch invocation that quits, so the prefab has to be built by calling `VRMImporterContext`
and `VRMEditorImporterContext.SaveAsAsset` directly.

The project is back on `com.vrmc.vrm` 0.131.2, with the manifest restored from a copy taken
before the swap.

## Visemes from a VRM's own expressions

A converted VRM had no visemes and no blink: the report told the reader to assign fifteen slots by
hand. VRM names five vowels, so five of them can be filled.

Basis keeps visemes in the Oculus order, verified against `AvatarSDKVisemes` in the Basis SDK:
slots 10 to 14 are aa, E, ih, oh, ou. VRM 1.0 names them `Aa`, `Ee`, `Ih`, `Oh`, `Ou` as preset
fields and VRM 0.x names them `A`, `E`, `I`, `O`, `U` as clip names, so one table covers both.
The ten consonants stay unset: filling them with a vowel's shape would move the mouth on the
wrong sound.

A viseme slot holds one blendshape, so an expression that moves several is reported as
`vrm.visemeCompound` rather than reduced to one of them. Basis reads all fifteen from one mesh, so
an avatar that spreads its vowels over several renderers gets whichever carries the most, and the
rest are reported as `vrm.visemeMeshSplit`. Only the two-eyed `Blink` fills the blink slot; the
one-eyed expressions are not it.

Verified on both real avatars: `FaceVisemeMovement` came out
`[-1 x10, Fcl_MTH_A, Fcl_MTH_E, Fcl_MTH_I, Fcl_MTH_O, Fcl_MTH_U]` with blink on `Fcl_EYE_Close`.

The four fixture-based tests skip: the Basis Avatar component is only planned for an avatar with a
humanoid rig, and the hand-written VRM fixtures have no rig. Giving them one means authoring a
humanoid `Avatar` asset with all fifteen required bones, which is the next thing worth doing here.
The mapping itself is covered by tests that need no fixture.

## The VRM fixtures got a rig, and a face worth binding to

The four viseme tests skipped because the Basis Avatar component is only planned for an avatar
with a humanoid rig, and the fixtures had none. Both now carry one: hips through head with arms,
legs and eyes, eighteen bones written into the fixture text, with the head the fixture already had
reparented under the new neck rather than duplicated.

An `Avatar` is a native asset Unity builds from a live hierarchy and validates, so it cannot be
hand-written: `FixtureHumanoidGenerator` builds one per fixture from the fixture's own bones,
matching Unity's bone names, and `Regenerate Test Fixtures` runs it. The same generator puts eight
blendshapes on `SampleFace`, in place so the mesh keeps its guid, since blendshape frames are the
other thing in these fixtures that cannot be typed.

The expression fixtures gained the rest of the vowels, a blink, and one vowel that moves two
shapes at once. So the tests now cover four slots filled by shape name, blink by index, the
compound case reported rather than guessed, and, with a look at offset and a first person flag
added to the 1.0 object asset, the eye position and first person codes for both formats.

Two lessons from doing it:

- **Edit YAML one document at a time.** A regex with `.*?` across a whole prefab matches the next
  document's field, not the intended one. The first attempt silently reparented the wrong
  transform and put the eyes under the root.
- **The 0.x fixture already used 100003.** A hand-picked file id has to be checked against every
  file it goes into; Unity's "Duplicate identifier" is the only warning, and it refuses to load
  the prefab at all.

236 tests, none skipped. `AVrm0EyeOffsetBecomesTheAvatarsEyePosition` asserted the `noRig` path
and now asserts the eye position it writes instead.

## 0.2.0 is out

Tagged `v0.2.0`, signed, and live on all three channels: the GitHub release (zip,
`.unitypackage`, signed `.tgz` with a Unity attestation, and the bare `package.json`), the VPM

## Audited what is actually built

The question was whether the feature list describes real code. It does, with two documentation
errors and one real gap. What was checked, and against what:

- **Every Basis, Vixxy and jiggle type and field the writers touch exists.** The `SerializedObject`
  string literals matter most, because a wrong name fails silently rather than at compile time.
  All of them resolve: Vixxy's `activations`, `subjects`, `properties`, `component`, `selection`,
  `targets`, `childrenOf`, `exceptions` and the menu item's `title`, `titleSelection`,
  `presentation`, `control`; jiggle's `hasSerializedData`, `serializedVersion`, `rootBone`,
  `excludeRoot`, `lockFromGrabbing`, `maxGrabStretch`, `excludedTransforms`, `jiggleColliders`.
- **Two semantic claims re-verified against Basis source, not docs.** `AvatarEyePosition` really
  is a packed `(height above root, forward)` pair with no lateral component, so reducing
  VRChat's Vector3 and reporting the sideways drop is right.
  `BasisTransformMapping.FindTwistBone` really does take the first direct child whose name
  contains "twist" or "roll", case-insensitively, which is what `RigReadiness` implements.
- **The script identity table is real.** 25 of its 53 guids appear in the reference VRChat
  project's own prefabs, and the VRM ones in the shipped fixtures. The rest are components
  neither project happens to use. All 32 Modular Avatar kinds are named, as claimed.
- **No vacuous tests.** Every test method asserts something, and the run skips none, so the count
  is not padded by fixtures that quietly went missing. Three of them (`ToggleDirection`,
  `ToggleTracingDiagnostic`) are print-only smoke harnesses that end in `Assert.Pass`; they
  exercise the pipeline but pin no behaviour, which is worth knowing when reading the total.

Fixed: the report guide named `constraint.solveInLocalSpace`, but the code emits
`constraint.solveInLocalSpace.dropped`, so anyone searching a report for it found nothing. The
other 24 documented codes are exact. A comment in `ModularAvatarDocumentReader` put the puppet
control types at "104 and up"; they are 201, 202 and 203, confirmed against real expression
menus. Only the comment was wrong, `VrcExpressionControlType` already had it right.

The roadmap claimed motion a menu switches on was still to do. It shipped in 0.2.0, has a
diagnostic (`motion.switched`), a test and a changelog entry. Corrected.

## Prefab variants converted with nothing

Converting the three real Shinano prefabs headlessly found this, and no test would have.

`Shinano_AMS.prefab` is a variant of `Shinano.prefab`. Its own file holds 0 PhysBones where the
base holds 61, because a variant stores only what it overrides. The conversion read the variant
alone, so it planned no physics, reported its five inherited colliders as unresolved, and said
nothing about the 61 it never saw. Silence there breaks the rule the whole project rests on.

Fixed, not just reported. Every prefab above a variant is read as well, and the components found
there are resolved onto the variant's own objects. That last part is what made it cheap:
`PrefabObjectResolver` already indexed live objects by the guid and file id of the object they
correspond to, for nested prefabs, and a variant's inherited objects carry exactly that
identity. Resolving the base's file ids through it lands them on the variant's own transforms,
so the planner, mappers and writers needed no change at all. `Index` now walks the whole
correspondence chain rather than one step, so a variant of a variant works too.

On the real avatar: PhysBones 0 to 61, constraints 2 to 30, colliders 5 to 16, Vixxy controls
0 to 11, and the descriptor went from "none, added empty" to converted. The counts are additive
against the two files rather than doubled, checked against both. The two prefabs that are not
variants read identically to before.

The first version of the diagnostic fired on `Shinano.prefab` itself, because a prefab built on
an FBX is also a variant as far as Unity is concerned. A model holds no authored components, so
there is nothing to miss; the check now ignores a base of type `Model`. That false positive
appeared in the first report generated after the change, which is the argument for generating one.

## Reading three real reports

61 PhysBones and 11 colliders found, which is exactly what the prefab file contains. The counts
are right. Two things in the report that look like bugs are not:

- `physbone.radius.negative` on a radius of -29.73. The avatar really does have that, twice.
  Clamped and reported, which is correct.
- Six jiggle rigs rooted at `Breast_1.L` and `.R`, three per side. The avatar really does carry
  three PhysBones on each, which is how a jiggle-strength toggle is usually built. 61 in, 61 out.

`source.unknownScript` named `AvatarModifySupportBehaviour`, a third party VRChat tool, so the
unknown path works. It is in the identity table now: its behaviour implements VRChat's
`IEditorOnly` and holds nothing but exported blendshape and colour preset data for its own
editor window, so there is no runtime behaviour to carry and nothing is lost by not converting
it. Reported as `source.editorOnlyTool`, a category that can take the next such tool.

## Vixxy cannot express two inputs

The roadmap wondered whether `HVRVixxyAggregator` could carry layers steered by two parameters,
and the axis puppets with them. It cannot, and not because it is switched off: its entire body
sits behind `HVR_AGGREGATOR_IS_AVAILABLE`, which nothing defines; its `IHVRVixxyAggregator` base
is commented out; and the `orchestrator.ProvideValue` it calls does not exist on
`HVRVixxyOrchestrator`, so it would not compile if the define were turned on. The orchestrator
does keep `RegisterAggregator` and an aggregator tick, so this is unfinished upstream work.

Both remaining toggle items therefore wait on Vixxy rather than on us. Recorded in the roadmap
so the question is not reopened.

## The five unresolved colliders were the same bug

`Shinano_AMS` reported 16 colliders where the avatar has 11, five of them unresolved. They are
`stripped` entries: a prefab built on another writes one per component of the base it needs to
refer to, carrying the script identity and nothing else, no data and no owning object. Reading
one as a component gave a collider with nothing in it, which is what "unresolved" was. Once the
base was read too, the same collider was counted twice.

`UnityYamlDocument.Stripped` was parsed and never used outside the resolver. The reading passes
skip stripped documents now; the resolver still keeps them, because following one to the object
it corresponds to is exactly how a nested prefab's components resolve. Colliders on that avatar
went 16 to 11, the five false diagnostics are gone, and the two prefabs that are not variants
did not move.

Worth remembering: this was in before today's variant work, just quieter. It only became a
double count once the base was read.

## Audit before the release

- **Tests**: 206, all passing, none skipped, no `error CS`.
- **Dead code**: four unreferenced public members removed, `ProductInfo.Tagline`,
  `PrefabObjectResolver.TryGetDocument`, and the `ClassIdTransform` and `ClassIdPrefabInstance`
  constants. Nothing else in `Editor/` is referenced only at its declaration.
- **Docs**: all 27 diagnostic codes in the report guide exist in the code, checked both ways.
- **Comments**: the resolver said "two routes" and has three; `ConversionSource` did not mention
  variants. Both corrected.
- **Layering holds**: `Mapping/`, `Model/` and `Reporting/` contain no `AssetDatabase`, `Undo` or
  `PrefabUtility`. In `Sources/` only the resolver and the VRM object reader touch the
  AssetDatabase, both by necessity.
- The VRM page still tells the reader to unpack a `.vrm` completely, and it is still right: an
  imported `.vrm` is binary, so a prefab that only points back at it has nothing to read. That is
  the same reason a variant of a model is deliberately not followed.

## Timing the window, because it felt slower

Measured rather than guessed. Planning the 61 PhysBone avatar takes about 270 ms, and the
variant check added for this work takes 0.01 to 0.02 ms of it, five thousandths of a percent.
The reading passes now run once per file in a variant's chain, so a variant costs roughly one
extra pass over the base's file and a plain prefab costs nothing new.

The window plans in `OnEnable` and when the target changes, not on repaint, so that 270 ms is
paid once on opening rather than every frame. What is left to explain a slower open is the
domain reload after a script change, which is unrelated to the package. If it stays slow with no
recompile pending, the thing to do is time `Rescan` rather than guess again.

## The OpenUPM description was wrong

It claimed the package converts props, which it does not, framed the sources as "other social VR
platforms", which `AGENTS.md` rules out because a VRM is a format rather than a platform, and
omitted VRM and authored motion entirely. Replaced with the `package.json` description, which is
accurate and already the canonical wording. Open as openupm/openupm#6853, waiting to be merged.

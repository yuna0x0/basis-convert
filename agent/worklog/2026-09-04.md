# 2026-09-04

The release audit for 0.4.0, and one gap it found.

## The VRM 0.x component branches are gone

They could not fire. Verified first: a 0.x `.vrm` re-imported with UniVRM 1.0 is claimed by
`VrmScriptedImporter`, arrives as a binary asset of 122 components with `Vrm10Instance` set and
every one of its 22 chains marked 1.0, and converts exactly as the native 1.0 avatar does, down to
the same visemes and eye position. The 0.x fields on the reader's result stayed null throughout.

So the only combination those 248 lines served was 0.x components inside a binary asset, which no
importer produces: UniVRM 0.x writes a prefab, UniVRM 1.0 migrates. Removed, with the identity
table left alone so a 0.x component is still named rather than reported as an unknown script.
Recorded in `agent/decisions/0015`. 236 tests, no compile errors.

## A prefab saved from a .vrm without unpacking read as empty

The audit's own sweep found it: `source.notUnpacked` fires for a prefab that is a variant of an
imported model, because the model holds the components and an FBX carries none. A `.vrm` model
does carry them, as live types, and the component reader was only ever run on a source whose own
file is binary, so a prefab saved from a `.vrm` instance still converted as empty and told the
user to unpack.

`ReadModelComponents` reads the model's components and resolves them onto the prefab's own
objects through `PrefabObjectResolver.CreateForInherited`, whose inherited mode already matches a
base object's local id to the object that corresponds to it. Verified on a prefab saved from
AvatarSample_B: 22 rigs, 28 colliders, 18 expressions, 28 written, `source.notUnpacked` gone and
`source.modelRead` in its place. No fixture can cover it, since it needs a binary model with live
components, so it is verified against the real avatar and recorded here.

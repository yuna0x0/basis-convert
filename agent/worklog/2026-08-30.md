## The spike, and what it found

The reader design rested on one unverified assumption: that a component in a prefab file whose
script is missing can be tied back to the live GameObject carrying it. Measured that before
building on it. The direct approach does not work.

Fixture: a real avatar with 61 VRCPhysBone, 28 VRCRotationConstraint, 11 VRCPhysBoneCollider,
1 VRCAvatarDescriptor and 1 PipelineManager, across 102 GameObject documents of which **95 are
stripped**, meaning they are back references into nested prefabs rather than full definitions.

Measured:

| approach | result |
|---|---|
| `AssetDatabase.TryGetGUIDAndLocalFileIdentifier` on the document's own fileID | 8/102 components, 1/95 stripped GameObjects |
| reaching the missing-script components through `SerializedObject`'s `m_Component` array | 0 reachable; they come back as null from `LoadAllAssetsAtPath` |
| `m_CorrespondingSourceObject` matched against `PrefabUtility.GetCorrespondingObjectFromSource` | **95/95 stripped, 0 ambiguous** |

So `PrefabObjectResolver` uses both routes: local file identifier for objects authored directly
in the file, corresponding-source for everything coming from a nested prefab, disambiguated by
the prefab instance handle when one nested prefab is used more than once. Neither route matches
on names, so duplicate bone names cannot cause a mismatch. The hierarchy path fallback the plan
budgeted for is not needed.

The 102 nulls also settle a related question: the missing-script components are genuinely
unreachable through the object API, so reading the YAML is not a shortcut, it is the only way.

### A false negative worth remembering

The first run of this diagnostic reported 9 live transforms against 95 stripped documents, which
looked like the approach failing outright. The real cause was that the avatar's FBX was a
133 byte **Git LFS pointer** rather than the real 16 MB file, so the armature never imported.
Check that binary assets actually materialised before believing a result about hierarchy.

## Working against a Basis clone

Develop in a branch of the Basis clone and link the package in, as `CONTRIBUTING.md` describes.
Two things bit here and are worth knowing:

- **Take the branch from wherever the test assets actually live.** Git LFS is driven by
  `.gitattributes`, so a branch that does not carry those files hands you pointer files instead
  of assets, silently. That is what produced the false negative above.
- Every headless test run leaves regenerated editor output in the Basis working tree. It is
  noise; do not commit it, and do not mistake it for a change of yours.

## Reader and mapper

Both done, 22 tests green. Two findings worth carrying forward.

**Falloff curves carry across untouched.** Jiggle evaluates a curved parameter as
`value * curve.Evaluate(t)` over normalized distance from the chain root, which is exactly what
VRChat does. So a PhysBone curve becomes a jiggle curve with no resampling. This matters more
than it sounds: **all 61** PhysBones in the reference avatar have falloff curves, so flattening
them to scalars would have degraded every single rig.

**`advancedToggle` gates half of jiggle's parameters.** `ToJigglePointParameters` ignores
`stretch`, `collisionRadius`, `ignoreRootMotion`, `soften` and `rootStretch` unless it is on,
and `collisionRadius` also needs `collisionToggle`. Writing them with the toggle off is a silent
no-op.

Reference avatar shape, for calibration: 61 PhysBones, 11 colliders, 54 Simplified against 7
Advanced, limit types 31 Angle / 25 Polar / 3 Hinge / 2 None, 2 bones with `ignoreTransforms`.
**25 of 61 use Polar limits**, which jiggle cannot express, so that approximation is not a
corner case here, it is nearly half the rig.

## Writer

`JiggleRigWriter` produces real `JiggleRig` components, starting from the jiggle package's own
preset prefabs and overwriting only what the source determined. 29 tests green.

**Chain splitting turned out to be unnecessary.** The Basis docs say paired features need one rig
each, but `JigglePhysics.Visit` recurses into every valid child, and `excludeRoot` pins the root
rather than removing it. One rig covers every branch below its root. See `../decisions/0006`.
That is the second doc claim the shipped code contradicts, after the sphere-only collider claim.

**Curves cannot be written through `SerializedObject` on this component.** The property holds the
right curve before `ApplyModifiedProperties` and reads back as the unit curve after, while
`value` and `curveEnabled` survive. Every PhysBone in the reference avatar has curves, so this
would have flattened all of them while appearing to work. The writer uses
`GetInputParameters`/`SetInputParameters` for the parameter block instead, after the
SerializedObject apply so the stale snapshot does not overwrite it.

Also: assembly references are not transitive, so the test assembly needs its own reference to
the jiggle assembly even though the editor assembly already has one.

## Pipeline

`AvatarJigglePlanner` reads and maps without changing anything; `AvatarJiggleConverter` applies a
plan. The plan is read from a prefab asset and applied to whichever hierarchy is being converted,
usually a scene instance, with transforms located by sibling-index path rather than by name.

On the reference avatar: 61 PhysBones found, 61 rigs planned, 0 unresolved, 61 written, 0
skipped, and one undo reverts all of it.

Diagnostic totals from that run, useful as a baseline: 338 mapped, 156 approximated, 209
dropped, 64 warnings.

Two numbers from the first run looked wrong and were worth checking against the raw file rather
than accepting:

- `isAnimated` warned 61 times out of 61. That is real: this avatar has it set on every
  PhysBone. Correct, but it means the report has to group by code or it will be unreadable.
- `collider.capsuleRotation.snapped` fired 62 times against 11 colliders, of which only 3 are
  rotated at all. That was a bug: each PhysBone re-mapped the colliders it referenced, so a
  shared collider reported itself once per referencing rig. Colliders are now mapped once for
  the avatar and shared, and the count is 3.

## Window and report

`Tools > Basis Convert > Convert VRChat PhysBones`, plus a hierarchy context entry. Scan, review,
convert. Plain IMGUI rather than Basis's `BasisEditorUI`: matching their look would mean
depending on their editor internals, which is a poor trade for a cosmetic gain given how much
else here already reaches into private fields.

The report groups diagnostics by code. Listing them raw is unusable, since one avatar produces 61
identical `isAnimated` warnings.

Reading the generated report found a mapping flaw the tests had not: a PhysBone limit of 180
degrees, which is effectively unconstrained, was being clamped to jiggle's maximum of 90 and
reported as a clamp. That makes the converted bones *tighter* than the original. Wider-than-90
limits are now dropped instead, with a diagnostic saying why. Worth repeating: read the output,
not just the test results.

## Constraints

All six VRChat constraint types now convert. The mapping is the most direct in the package,
since both systems follow Unity's built-in constraints, so most fields transfer unchanged.

**The three missing fileIDs were computed rather than extracted.** Unity derives a DLL type's
fileID by hashing `"s\0\0\0"` plus namespace and type name with MD4 and taking the first four
bytes little-endian. Implementing that reproduced all thirteen identities already read off real
assets, so the same derivation was used for Parent, Scale and LookAt, which the reference avatars
do not contain. Marked as computed in the table. This also means any future VRChat type can be
added without needing a sample asset or the SDK.

The pipeline types were renamed off `AvatarJiggle*` to `AvatarConversion*` now that the package
converts more than jiggle, and the menu entry is Convert VRChat Avatar.

On the reference avatar: 28 constraints found, 28 planned, 28 written, all sources resolved.
None of them retarget, so the relocation path is covered by unit tests rather than by that
avatar.

Two mechanical gotchas, both previously seen: assembly references are not transitive, so the
test assembly needed `BasisSDK` added; and note that our `yuna0x0.Basis.*` namespace can shadow
Basis's own `Basis.*` if it is referenced inline from inside our namespace. Keep `using`
directives at file scope.

   `../decisions/0007`. The marker-component approach was prototyped first and abandoned:
   an editor-assembly MonoBehaviour cannot be attached to a GameObject at all, so it would have
   required shipping a runtime assembly purely for bookkeeping.
3. Done: the avatar descriptor. View position becomes Basis's height-and-forward pair, the
   fifteen visemes map positionally because both systems use the same order, and blink takes the
   first of VRChat's three eyelid blendshapes.

   Two things needed care. VRChat writes `eyelidsBlendshapes` as a **hex byte blob** rather than
   a sequence, so it needs decoding as little-endian int32s; reading it as a string would have
   silently lost the blink shape. And `BasisAvatar` is deliberately excluded from the replace
   sweep and updated in place instead, because Basis fills the animator, human scale, renderer
   list and mouth position itself the first time its inspector opens, and only fills values that
   are still empty. Removing the component each re-convert would throw that away.

# 2026-08-30

First working session. Turned earlier research on migrating VRChat avatars to Basis into a
package skeleton, a reader and a mapper.

## Done

- Researched the Basis avatar API, the jiggle physics package, the VRChat serialized formats,
  Basis packaging conventions, and the trademark and menu placement rules. Written up in
  `agent/research/` and `agent/decisions/`.
- Created the repo, the package `com.yuna0x0.basis.convert`, and the editor and test assemblies.
- Wrote `UnityYamlScanner`, `UnityYamlDocument`, `KnownScriptIdentities`, `PrefabObjectResolver`.
- Set up the Basis clone for development, see below.

## The spike, and what it found

The reader design rested on one unverified assumption: that a component in a prefab file whose
script is missing can be tied back to the live GameObject carrying it. Measured that before
building on it. The direct approach does not work.

Fixture: a real avatar with 61 VRCPhysBone, 28 VRCRotationConstraint, 11 VRCPhysBoneCollider,
1 VRCAvatarDescriptor and 1 PipelineManager, across 102 GameObject documents of which **95 are
stripped**, meaning they are back references into nested prefabs rather than full definitions.

Measured:

| approach | result |
|---|---|
| `AssetDatabase.TryGetGUIDAndLocalFileIdentifier` on the document's own fileID | 8/102 components, 1/95 stripped GameObjects |
| reaching the missing-script components through `SerializedObject`'s `m_Component` array | 0 reachable; they come back as null from `LoadAllAssetsAtPath` |
| `m_CorrespondingSourceObject` matched against `PrefabUtility.GetCorrespondingObjectFromSource` | **95/95 stripped, 0 ambiguous** |

So `PrefabObjectResolver` uses both routes: local file identifier for objects authored directly
in the file, corresponding-source for everything coming from a nested prefab, disambiguated by
the prefab instance handle when one nested prefab is used more than once. Neither route matches
on names, so duplicate bone names cannot cause a mismatch. The hierarchy path fallback the plan
budgeted for is not needed.

The 102 nulls also settle a related question: the missing-script components are genuinely
unreachable through the object API, so reading the YAML is not a shortcut, it is the only way.

### A false negative worth remembering

The first run of this diagnostic reported 9 live transforms against 95 stripped documents, which
looked like the approach failing outright. The real cause was that the avatar's FBX was a
133 byte **Git LFS pointer** rather than the real 16 MB file, so the armature never imported.
Check that binary assets actually materialised before believing a result about hierarchy.

## Working against a Basis clone

Develop in a branch of the Basis clone and link the package in, as `CONTRIBUTING.md` describes.
Two things bit here and are worth knowing:

- **Take the branch from wherever the test assets actually live.** Git LFS is driven by
  `.gitattributes`, so a branch that does not carry those files hands you pointer files instead
  of assets, silently. That is what produced the false negative above.
- Every headless test run leaves regenerated editor output in the Basis working tree. It is
  noise; do not commit it, and do not mistake it for a change of yours.

## Reader and mapper

Both done, 22 tests green. Two findings worth carrying forward.

**Falloff curves carry across untouched.** Jiggle evaluates a curved parameter as
`value * curve.Evaluate(t)` over normalized distance from the chain root, which is exactly what
VRChat does. So a PhysBone curve becomes a jiggle curve with no resampling. This matters more
than it sounds: **all 61** PhysBones in the reference avatar have falloff curves, so flattening
them to scalars would have degraded every single rig.

**`advancedToggle` gates half of jiggle's parameters.** `ToJigglePointParameters` ignores
`stretch`, `collisionRadius`, `ignoreRootMotion`, `soften` and `rootStretch` unless it is on,
and `collisionRadius` also needs `collisionToggle`. Writing them with the toggle off is a silent
no-op.

Reference avatar shape, for calibration: 61 PhysBones, 11 colliders, 54 Simplified against 7
Advanced, limit types 31 Angle / 25 Polar / 3 Hinge / 2 None, 2 bones with `ignoreTransforms`.
**25 of 61 use Polar limits**, which jiggle cannot express, so that approximation is not a
corner case here, it is nearly half the rig.

## Writer

`JiggleRigWriter` produces real `JiggleRig` components, starting from the jiggle package's own
preset prefabs and overwriting only what the source determined. 29 tests green.

**Chain splitting turned out to be unnecessary.** The Basis docs say paired features need one rig
each, but `JigglePhysics.Visit` recurses into every valid child, and `excludeRoot` pins the root
rather than removing it. One rig covers every branch below its root. See `../decisions/0006`.
That is the second doc claim the shipped code contradicts, after the sphere-only collider claim.

**Curves cannot be written through `SerializedObject` on this component.** The property holds the
right curve before `ApplyModifiedProperties` and reads back as the unit curve after, while
`value` and `curveEnabled` survive. Every PhysBone in the reference avatar has curves, so this
would have flattened all of them while appearing to work. The writer uses
`GetInputParameters`/`SetInputParameters` for the parameter block instead, after the
SerializedObject apply so the stale snapshot does not overwrite it.

Also: assembly references are not transitive, so the test assembly needs its own reference to
the jiggle assembly even though the editor assembly already has one.

## Pipeline

`AvatarJigglePlanner` reads and maps without changing anything; `AvatarJiggleConverter` applies a
plan. The plan is read from a prefab asset and applied to whichever hierarchy is being converted,
usually a scene instance, with transforms located by sibling-index path rather than by name.

On the reference avatar: 61 PhysBones found, 61 rigs planned, 0 unresolved, 61 written, 0
skipped, and one undo reverts all of it.

Diagnostic totals from that run, useful as a baseline: 338 mapped, 156 approximated, 209
dropped, 64 warnings.

Two numbers from the first run looked wrong and were worth checking against the raw file rather
than accepting:

- `isAnimated` warned 61 times out of 61. That is real: this avatar has it set on every
  PhysBone. Correct, but it means the report has to group by code or it will be unreadable.
- `collider.capsuleRotation.snapped` fired 62 times against 11 colliders, of which only 3 are
  rotated at all. That was a bug: each PhysBone re-mapped the colliders it referenced, so a
  shared collider reported itself once per referencing rig. Colliders are now mapped once for
  the avatar and shared, and the count is 3.

## Window and report

`Tools > Basis Convert > Convert VRChat PhysBones`, plus a hierarchy context entry. Scan, review,
convert. Plain IMGUI rather than Basis's `BasisEditorUI`: matching their look would mean
depending on their editor internals, which is a poor trade for a cosmetic gain given how much
else here already reaches into private fields.

The report groups diagnostics by code. Listing them raw is unusable, since one avatar produces 61
identical `isAnimated` warnings.

Reading the generated report found a mapping flaw the tests had not: a PhysBone limit of 180
degrees, which is effectively unconstrained, was being clamped to jiggle's maximum of 90 and
reported as a clamp. That makes the converted bones *tighter* than the original. Wider-than-90
limits are now dropped instead, with a diagnostic saying why. Worth repeating: read the output,
not just the test results.

## Constraints

All six VRChat constraint types now convert. The mapping is the most direct in the package,
since both systems follow Unity's built-in constraints, so most fields transfer unchanged.

**The three missing fileIDs were computed rather than extracted.** Unity derives a DLL type's
fileID by hashing `"s\0\0\0"` plus namespace and type name with MD4 and taking the first four
bytes little-endian. Implementing that reproduced all thirteen identities already read off real
assets, so the same derivation was used for Parent, Scale and LookAt, which the reference avatars
do not contain. Marked as computed in the table. This also means any future VRChat type can be
added without needing a sample asset or the SDK.

The pipeline types were renamed off `AvatarJiggle*` to `AvatarConversion*` now that the package
converts more than jiggle, and the menu entry is Convert VRChat Avatar.

On the reference avatar: 28 constraints found, 28 planned, 28 written, all sources resolved.
None of them retarget, so the relocation path is covered by unit tests rather than by that
avatar.

Two mechanical gotchas, both previously seen: assembly references are not transitive, so the
test assembly needed `BasisSDK` added; and note that our `yuna0x0.Basis.*` namespace can shadow
Basis's own `Basis.*` if it is referenced inline from inside our namespace. Keep `using`
directives at file scope.

## Repeated conversions

Converting twice stacked a second set of components. It now confirms, then removes the ones on
the transforms the new conversion writes to, and writes. Scoped by the plan, with no state stored
on the avatar. See `../decisions/0007`.

A marker component recording what was created was prototyped first and abandoned: a MonoBehaviour
in an editor-only assembly cannot be attached to a GameObject at all, so it would have meant
shipping a runtime assembly purely for bookkeeping.

## Avatar descriptor

View position becomes Basis's height-and-forward pair, the fifteen visemes map positionally
because both systems use the same order, and blink takes the first of VRChat's three eyelid
blendshapes.

Two things needed care. VRChat writes `eyelidsBlendshapes` as a **hex byte blob** rather than a
sequence, so it needs decoding as little-endian int32s; reading it as a string would have lost
the blink shape silently. And `BasisAvatar` is deliberately excluded from the replace sweep and
updated in place instead, because Basis fills the animator, human scale, renderer list and mouth
position itself the first time its inspector opens, and only fills values that are still empty.
Removing the component each re-convert would throw that away.

## Dynamic Bone

Maps more cleanly than PhysBones: damping is jiggle's drag and inert is its ignoreRootMotion,
both on the same scale, so only the return-to-pose force needs judgement. A component driving
several roots becomes one rig per root, since those are separate chains rather than branches.

This also gained the first **committed fixture**: a hand-authored prefab with a Dynamic Bone, a
collider and a two-bone chain, written as plain YAML. No purchased asset, so the pipeline is
covered on any machine rather than only where the reference avatar exists.

## Rig readiness

Reports what Basis's full-body IK will make of the humanoid rig: whether the bones it maps are
all present, whether a Jaw bone is mapped that the Basis setup guide asks to be cleared, whether
the eye bones are mapped for gaze, and which arm bones have a twist child. The Jaw mapping can be
cleared from the window; that edits the model importer rather than the scene, so it is confirmed
separately and is not covered by undo.

The roadmap said to verify the twist behaviour against the code before building it, and that was
worth doing. It works exactly as the constraints page describes, first direct child whose name
contains `twist` or `roll`, case-insensitively, but it lives in
`BasisTransformMapping.FindTwistBone` in `com.basis.common`. The `BasisFullIKConstraintJob` the
page attributes it to does not exist in the shipped source; the IK is in
`com.basis.eeriemovement`. Our lookup mirrors theirs so the report matches what Basis will find.

The check is skipped for anything that is not an avatar. The first run warned that the Dynamic
Bone fixture had no Animator, which is true and useless: props and clothing carry physics
components and have no humanoid rig.

On the reference avatar: bones complete, both eyes mapped, no Jaw mapping to clear, and no twist
children under any of the four arm bones, so Basis will simply not apply arm twist there.

## What does not convert

The report claimed to list everything approximated or dropped while saying nothing about the
expression and animation systems, which is most of what an avatar's owner actually notices. The
reference avatar has an expression menu, expression parameters and four custom animation layers,
and the report was silent on all of it.

Those are now read from the descriptor and reported as dropped, with what to do instead: Vixxy
for toggles, Authored Motion for looping movement. VRChat contacts are counted and reported the
same way. A layer only counts when it has a controller that is not VRChat's stock one, since
those are the ones somebody authored.

Nothing here converts, and none of it is likely to: Basis has no playable layers, no synced
parameter list and no contact system. The value is in saying so.

## Expression menus, first slice

Reading the menu tree and parameters, ahead of converting any of it. Both are VRChat SDK
ScriptableObjects, so in a Basis project their scripts are missing and they are read from YAML
the same way components are. Submenus are separate assets referenced by guid, so the tree is
walked rather than read from one file, with visited guids skipped so a cycle cannot recurse
forever.

One parsing trap: a menu control has a `name`, and its nested `parameter` block has a field also
called `name`. Reading them without tracking which block is open swaps the control's label with
the parameter it drives. There is a test for exactly that.

The reference avatar: 36 controls across 7 menus, 26 of them toggles, plus 19 parameters. That
is the size of the rebuild, and the report now says so instead of "the avatar has an expression
menu".

## Avatars that never came from VRChat

Dynamic Bone is an ordinary Unity asset and plenty of avatars use it with no VRChat involvement.
Traced what happened to one of those, and most of the pipeline already handled it: the Dynamic
Bone identity is a loose script guid, so reading is platform independent, and the rig check keys
off the humanoid rig rather than off a descriptor.

The gap was the avatar component. Nothing created a `BasisAvatar` without a VRChat descriptor, so
such an avatar converted its physics and was still not usable. It now gets one whenever the root
has a humanoid rig, created empty, with the report saying that Basis will fill the animator,
scale, renderers and positions itself and that visemes and blink have to be assigned by hand.
A prop still gets nothing: the test is the rig, not the presence of physics.

The window wording claimed VRChat throughout, including the menu entry, which misdescribed what
the tool does. Now `Convert Avatar`.

Scanning a binary asset was working by accident: an FBX yields no YAML documents because nothing
matches the header pattern, but only as long as reading its lines does not throw. That is now
explicit.

## The animation layer enum was wrong

Resolving the reference avatar's animator controllers to their slots gave a nonsense answer: the
file named `Shinano_FX` sat in the Sitting slot, and `Shinano_Action` in the FX slot. Two possible
explanations, an author mistake or a wrong enum, so it was settled by evidence rather than by
picking one: `Shinano_FX.controller` holds exactly the toggle parameters the expression menu
drives, so it is the FX layer whatever the slot number says.

Decompiling `VRCSDK3A.dll` settled it. The real ordering has `Deprecated0` at 1:

```
Base = 0, Deprecated0 = 1, Additive = 2, Gesture = 3,
Action = 4, FX = 5, Sitting = 6, TPose = 7, IKPose = 8
```

The ordering quoted everywhere, including in this project's own research note, omits
`Deprecated0`. With it the avatar's layers read as Base, Action, FX, Sitting; they are Base,
Gesture, Action, FX. The report had been stating that confidently and wrongly, and it is exactly
the kind of error that survives because the output still looks reasonable.

Worth remembering that the earlier research derived this from DLL metadata strings rather than
from the type, and got it wrong. Decompiling took one command.

## Tracing toggles to their layers

Reads the FX controller and the clips behind each menu toggle. Unlike everything else, an
AnimatorController is a native Unity type, so this goes through the editor API rather than YAML.

The first run resolved 13 toggles, two of which were wrong: a face parameter matched the Left
Hand and Right Hand gesture layers, where it appears as a **secondary** condition alongside
`GestureLeft`. A layer now counts as a toggle for a parameter only when that parameter is the
only one steering it, which drops those two and leaves 11 real ones.

Only clips holding a constant carry across, since a Vixxy control stores a value per choice
rather than a curve. On the reference avatar: 11 of 26 menu toggles trace to a layer, 9 of those
only switch objects and set blendshapes. The other two drive material properties, 14 of them in
one case.

## Emitting Vixxy controls

Reading the Vixxy source settled the encoding, and it is not what the field names suggest.
Switching an object is an **activation**, not a subject: `HVRVixxyActivation` holds a `Component`
and one bool per choice, and its own comment says to pass the Transform, "as GameObject is not a
component". Subjects with properties are for blendshapes and material values. The orchestrator
does not need creating; a control finds its own through `VixxySetup.EnsureInitialized`.

`choices` and `defaultValue` are public, the rest is internal to the assembly, so the activations
go through `SerializedObject`.

The first run produced zero controls. The rule was that an object had to be animated on both
sides of the toggle, and almost no VRChat toggle does that: one state animates and the other
leaves the object at whatever the avatar was authored with. That state is knowable rather than a
guess, so it is now read from the hierarchy, which is more accurate than assuming the opposite of
the animated side.

Four controls on the reference avatar: Skirt, Tights, Ear, Tail. Only toggles that purely switch
objects are built; ones that also set blendshapes are reported instead, because emitting half a
toggle would leave a control that looks finished and does part of the job.

## Blendshapes in Vixxy controls

Blendshapes are subjects rather than activations: a subject names the objects and carries a float
property per shape with a weight per choice, built exactly as Vixxy's own editor does it,
`fullClassName` of the renderer type, `variant` BlendShape, `propertyName` the shape. The property
list is a SerializeReference list, so entries go in as managed references.

The same authored-state rule applies as for objects: a shape set on only one side of the toggle
keeps the avatar's authored weight on the other, read from the renderer rather than assumed.

One bug this surfaced: controls with no object switching at all were being skipped, so a body
shape slider that only sets blendshapes produced nothing.

Nine controls on the reference avatar now, up from four: Sweater, Dress, Skirt, Tights, Boots,
Side bangs, Ear, Tail and Hip, with 13 blendshape properties between them. What remains
unconverted is the two toggles driving material properties.

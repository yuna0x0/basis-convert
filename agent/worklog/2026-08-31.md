# 2026-08-31

Released, renamed, and fixed the first bug found by wearing the result.

## Shipped

`v0.1.0`, `v0.1.1` and `v0.1.2` are out, through three channels:

- **GitHub releases**, built by `.github/workflows/release.yml` on a version tag. Each carries
  the bare `package.json`, a VPM zip, a `.unitypackage` and a signed `.tgz`. Tests are excluded
  from the artifacts, the way Modular Avatar, NDMF and Avatar Optimizer keep theirs out of a
  consumer's project.
- **The VPM listing** at `vpm.yuna0x0.com`, which reads those releases.
- **OpenUPM**, tracking `githubRelease` so it republishes the signed tarball rather than
  building its own. `signed: true` on every version.

The docs site is live on GitHub Pages and rebuilds when `docs/**` or the package manifest
changes, so the version it quotes cannot go stale: pages write `{{VERSION}}` and a Docusaurus
markdown preprocessor fills it in from `package.json`.

## Renamed to Watari

"Basis Convert" was the shape the trademark policy warns about, a bare `Basis <Word>` used as a
product name, while descriptive reference is separately permitted. The product is **Watari**, and
`displayName` is `Watari (Converter for Basis)`; menus are `Tools > Watari > Convert Avatar to
Basis`. Decision 0002 records the reasoning and the ecosystem evidence: Haï leads with `HVR`,
towneh's package carries no mark at all, and a bare `Basis <Word>` from a third party appears
nowhere.

The package id, the namespaces and the assembly names did not change. They are not what a user
reads, `basis` is a scope segment rather than a product name, and changing the id would mean a
second OpenUPM entry and orphaning what was published.

The repository moved to `yuna0x0/watari-basis`, so every URL followed.

## The first bug found by wearing it

A converted avatar's toggles were inverted: turning `Tail_OFF` on showed the tail. Eight toggles
on the reference avatar, and the whole suite passed throughout.

The mapper knew which side of a toggle animated each object and kept only whether both had. The
planner then had to decide which side to fill with the avatar's authored state, and decided from
the value:

```csharp
activation.Choices[activation.Choices[1] ? 0 : 1] = authored;
```

**A clip that switches an object off leaves the same value behind as a side that animated
nothing.** So the authored state landed on the side that had animated, and every one-sided toggle
came out backwards. Blendshapes had the identical fault; material properties did not, because
they already recorded which side set each channel.

`SetWhenOff` and `SetWhenOn` are now recorded per activation and per blendshape, and the fill
moved into `VixxyAuthoredDefaults`, which is a pure function of those flags. That made both
halves testable without an avatar, which matters: most of this suite is gated on a purchased
avatar and silently skips for anyone else.

## Upstream

Switching the Basis project to Android to export an avatar broke its compilation:
`SMModuleGlobalIlluminationURP` is declared under `#if BASIS_HAS_GI && !UNITY_ANDROID`, and one
camera test used it under `#if BASIS_HAS_GI` alone. Thirty-one other guards in those two packages
use both conditions. Fixed upstream as BasisVR/Basis#1024.

## A fixture avatar, and what it found

Sixteen of twenty-five test files were gated on a purchased avatar and did nothing without it.
`Tests/Editor/Fixtures/SampleAvatar` is now a hand-authored avatar: a prefab with missing-script
PhysBone, collider, constraint and descriptor components, an expression menu and parameters
asset, an FX controller and its clips. `SampleClothing` is the Modular Avatar half. The
controller and clips are generated rather than hand-written YAML, by
`Tools > Watari > Development > Regenerate Test Fixtures`, because an animator controller is
Unity's own asset type and the editor writes it correctly where hand-editing would not.

The fixtures found three bugs the reference avatar never did, each because the fixture exercised
a shape it does not have:

- A Modular Avatar menu item only became a control when the prefab also installed an expression
  menu, so clothing that installs a menu item alone converted nothing.
- The menu reader started a new control at any `-` line, so a radial's `subParameters` entry was
  read as a control of its own. Controls are recognised by indentation now.
- Modular Avatar object paths were rebased onto the component's own object. `AvatarObjectReference`
  resolves them against the avatar root instead, which is what `Get` does in Modular Avatar's own
  source.

## Selectors and puppets

The "15 of 26 toggles never trace" figure was wrong, and so was the diagnostic that produced it:
it counted menu controls against traced parameters. The avatar's 26 controls share **14
parameters**, of which **13 now trace**.

**Selectors** were most of the gap. Several menu controls share one int parameter and each
selects a value; Vixxy holds that natively as a control with a choice per value, and the reader
only understood two-state layers. Reader, resolver and writer are N-wide now.

**Radial puppets** are neither half found by the toggle path: the menu entry names its parameter
under `subParameters` rather than as its own, and the layer holds a blend tree rather than
transitions. Both are read, and the control is written with `presentation` set to `Slider`. The
tree's children are sorted by threshold and the two ends taken, because Vixxy interpolates
between choices in a straight line: the ends describe the sweep and anything between them is
approximated by that line, which is reported as `vixxy.puppetEnds`.

The suite is at 163 tests, all passing, none of them needing a purchased avatar.

## Authored motion

An FX layer with nothing steering it is animation that plays from the moment the avatar loads: a
tail that sways, an accessory that turns. A Basis avatar carries no animator layers, so the only
place for it is `BasisAuthoredMotion`, which replays a baked clip from a batched job.

The clip is baked the way Basis's own `BasisMotionClipBaker` does it, because the format is a
flat buffer rather than curves: sample through `AnimationMode`, read each bone's `localRotation`
as it lands, write `transformIndex * frameCount + frame`. Recording the rotation as it lands
rather than as the curve states it is what makes a clip authored against another rest pose replay
correctly, and it is why the bake needs a live hierarchy rather than the prefab the plan was read
from.

Two things worth remembering:

- **`HVR_VixxyPermitted` lists `BasisAuthoredMotion`.** A Vixxy activation may enable and disable
  one, which is the shape a toggled ambient motion should take when that is built.
- **A baked clip is a project asset, so an undo does not remove it.** Everything else a
  conversion writes disappears. The window, the docs and the changelog all say so, and the asset
  path is derived from the source clip so a second conversion overwrites rather than accumulates.

The fixture grew a `TailIdle` layer for this. Its first run wrote a baked clip into the package
and it was nearly committed: the tests now redirect every plan's output folder into the project
and delete it afterwards.

## Motion a menu switches on

The other half of the same feature. A toggle whose clip animates rather than switches was
reported and dropped whole; now the animation becomes a motion of its own and the control
switches the component. `HVR_VixxyPermitted` lists `BasisAuthoredMotion`, and a Vixxy activation
holds a `Component` rather than a GameObject, so this needs no new mechanism at either end: it is
an ordinary activation whose component happens not to be a Transform.

Three things this needed:

- **Order.** Motions are written before controls, because a control has to hold a component that
  does not exist until it is written. The converter keeps a map from planned motion to written
  component and resolves activations against it.
- **An index rather than a path.** `VixxyActivationPlan` gained `MotionIndex`; -1 means it
  switches an object by path as before. The planner pushes a null into `SourceTargets` for those
  so the two lists stay in step, and the writer's target list is `Component` rather than
  `Transform`.
- **A starting state.** The component is enabled or disabled to match the control's default
  choice, so an avatar nobody has touched looks right before Vixxy initialises.

The `vixxy.notSimple` test is narrower now: a clip is only dropped when it animates something
other than rotation, or drives something a control cannot hold at all.

## Layers with more than one condition

A layer was read as a toggle's only when exactly one parameter steered it. That rule was doing
two jobs at once, and separating them found coverage:

- **VRChat's own parameters are guards, not steering.** A gimmick that only runs for the wearer
  tests `IsLocal`; one that stops in a chair tests `InStation`. Nothing on Basis drives any of
  them, so a layer guarded that way is still the menu parameter's layer. The control is rebuilt
  and `vixxy.builtinGuard` says what it no longer waits for. `VrchatBuiltInParameters` holds the
  table, and an unrecognised name is treated as the avatar's own, which is the safe way round: it
  makes the layer look steered by two things and leaves it alone.
- **A built-in that steers a transition alone still owns the layer.** A gesture layer has a state
  per gesture, and reading it as a toggle's would take clips the toggle never selects. So a
  built-in only counts as a guard when every transition mentioning it also mentions the menu
  parameter.

Behind both: a layer where one value of the parameter reaches two different states is now refused
outright. Something other than the parameter is choosing between them, and the old code kept
whichever transition came first. That is a fix as much as a guard, and it is what makes the
gesture-shaped layer safe even when every transition names the parameter.

## An audit of what the new features touched

Four features landed in one session, so the whole thing got read back looking for what they
broke. Eight things, most of them found by reading rather than by a failing test:

- **Re-converting stacked Vixxy controls.** `FindReplaceable` scoped replacement by transform,
  which says nothing for components that all live on the avatar root: controls, menu items and
  motions. They are matched by the names the plan is about to write instead, so a control
  somebody made by hand survives. This had been true since Vixxy emission was written; the
  purchased-avatar tests that would have caught it skip on any other machine.
- **A control always started at its first choice.** The avatar declares a default per parameter
  and it was read but never used, so clothing authored on would have switched itself off at load.
  `DefaultOn` is a value now, matched against the choices the way Vixxy matches it.
- **A switched motion could be written without its control**, which would have played it
  permanently. It follows the control's selection now.
- **Narrowing a conversion did not narrow the toggle and motion diagnostics**, though that is
  the documented rule for every other category. They are separate lists on the plan now.
- **Modular Avatar's clip rebasing missed the animated rotations**, so a motion from clothing
  would have resolved against the wrong object.
- **A menu's labels were read as more subParameters**, because `subParameters: []` opened a block
  that nothing closed.
- **A second avatar descriptor was planned and reported before being discarded.** Clothing often
  ships one for previewing, and its visemes were being described as though they converted.
- **The re-convert dialog** counted everything that was not a jiggle rig as a constraint, and
  promised the whole thing was undoable.

Several reported counts and messages also described the converter as it was rather than as it is:
menu toggles "not converted yet", puppets with "no direct equivalent", every control claimed as
rebuilt.

## VRM, and what the project says it is

VRM spring bones convert now, in both formats. The path is the one the architecture was built
for: a VRM avatar in a Basis project carries its spring bones as missing scripts exactly as
VRChat components do, so this is a reader and a mapper and nothing else moved. UniVRM does not
have to be installed.

Ground truth came from three places rather than from documentation: UniVRM 0.131.0 in the Unity
package cache for the script guids and field names, its own `new_seedsan_10.prefab` sample for
how a spring is serialized, and a real `.vrm` file for what the parameters mean. All of it is in
`agent/research/vrm-spring-bones.md`, including that the guids are unchanged across the last
several UniVRM releases.

Two things worth keeping:

- **VRM 1.0 carries a parameter per joint, and jiggle evaluates its parameters over distance from
  the chain root.** Same axis, so a chain becomes a curve rather than an average. This is the
  second time that has been true, after PhysBone and Dynamic Bone falloff curves.
- **A spring names the bones it moves; a jiggle rig simulates the whole subtree.** An accessory
  hanging off a hair bone would start swinging, so anything the spring never named is excluded.

What a VRM carries besides physics is still unread: expressions, look-at, first-person, metadata.
The docs say so rather than implying a VRM avatar converts whole.

**The project describes itself differently now.** "From other social VR platforms" was too narrow
once VRM landed: a VRM file is a format, not a platform, and VRoid Studio is neither. The package
description, both READMEs, the docs, `AGENTS.md`, the roadmap scope, the GitHub description and
topics, and the VPM listing entry all say platforms and formats now.

## VRM expressions

The other half of VRM. An expression is a named set of blendshape weights, which is what a Vixxy
control holds once it has two choices, so this reuses the whole control path: subjects, authored
defaults, the writer, the menu item.

Both formats keep expressions in assets rather than on the avatar, so the components are followed
off disk the way an expression menu's submenus already were. The facts that mattered, all read
from UniVRM rather than assumed:

- **The weight scales differ.** VRM 1.0 runs 0 to 1 (`MorphTargetBinding.VRM_TO_UNITY` is 100);
  VRM 0.x is already on Unity's 0 to 100 scale, which `BlendShapeClipHandler` shows by passing
  the value straight to `SetBlendShapeWeight`. Getting this backwards would have made every 1.0
  expression a hundredth of itself.
- **A binding names a blendshape by its index in the mesh**, and Vixxy sets shapes by name, so
  the mesh is what translates. A shape that is no longer there is reported rather than guessed.

Visemes, blinking and looking around are not rebuilt: Basis drives those itself, and a menu item
the wearer has to hold down would fight it. They are reported as left to Basis.

The fixture grew a real mesh with named blendshapes, generated by
`Tools > Watari > Development > Regenerate VRM Face Mesh`, because testing an index-to-name
lookup without a mesh would test nothing. That makes the expression path covered end to end
rather than at the reader alone.

## Watch out for

- **A headless test run needs the editor closed.** `unity test` exits 6 and writes no results
  when the project is locked, which reads like a failure but is not one.
- **A green run is still not proof the code compiled.** The runner checks the project log for
  `error CS` and deletes the results file first, because Unity keeps the last good assemblies and
  reports their results when compilation fails.
- **The docs site and the package version are linked.** Bump the version and the site redeploys;
  do not hardcode a version number in a page.
